# 工程初始化方案

## 依据与边界

- 端划分以 `docs/design/中集系统功能端划分建议.md` V2.2（2026-09-19）为准；旧需求中的 PC 仓库/调度入口不再采用。
- 本期标准版、单工厂、初期 1～10 台车；工人、仓库、调度的日常业务均在小程序，管理端提供系统管理与支撑。
- 本次交付可编译的工程骨架、模块边界、基础接口、数据库与部署配置；不实现登录、订单状态机和实际车辆控制，不将占位页面作为业务交付。

## 架构选择

采用同仓库的双前端和模块化单体后端，各前端独立 npm 依赖及锁文件，后端使用 Maven。相较于微服务，该方案符合当前规模且运维简单；相较于仅建立空目录，可直接构建并验证接口约定。

- `miniprogram/`：uni-app Vue 3 TypeScript；主包放登录、消息、个人中心，业务按工人、仓库、调度、概览拆分分包。预留请求封装，工作区授权后续由服务端决定。
- `admin-web/`：Vue 3 TypeScript Vite Element Plus Vue Router；管理布局及按职责划分的延迟加载路由，初始化阶段仅显示未开通提示。
- `server/`：Java 17、Spring Boot 3、MyBatis；包根 `com.taskhub`，按业务域拆分 `domain`，公共响应与配置独立。
- `database/`：MySQL 8.4；初始化只建立应用元数据表验证数据库/MyBatis链路。业务表待状态机、权限及业务字段落实后逐模块迁移，不提前固化未确认模型。
- `deploy/`：Docker Compose 编排 MySQL、后端、Nginx 管理端；Nginx 转发 `/api/`，密钥通过环境变量传入。

## 模块边界

后端在 `com.taskhub.domain` 下预留 identity（身份、多角色及逐角色数据范围）、masterdata（仓库/点位/车辆/格口）、order、batch、dispatch、vehicle、ticket、notification、report、audit、integration（九识/微信）。模块当前仅有包说明，不暴露业务端点。

小程序业务分包预留申请/订单/取货、审批/批次/装货/工单、调度/车辆、概览/业务记录。管理端仅放账户、人员、权限、基础资料、营业规则、参数、既有接入、报表和审计，不放日常审批、派单、控制入口。

## 接口与安全基础

- 自有接口前缀 `/api`，响应 `{ code, message, data }`，成功 `code=0`，错误同时使用真实 HTTP 状态。
- ID（尤其 `dispatchId`）传输为字符串，后端统一序列化 Long；客户端不转换为 Number。
- `GET /api/health` 仅说明进程存活；`GET /api/ready` 使用 MyBatis 查询初始化元数据，数据库不可用返回 HTTP 503。
- 初始化阶段仅上述两个接口匿名可访问，其他接口默认拒绝。正式鉴权、角色与数据范围校验在身份模块实施，不用前端路由作为安全边界。
- 九识和微信凭证只在服务端管理，本次不建立虚假控制接口、不连接真实车辆。
- 本地开发环境可不启动数据库验证存活；就绪接口和部署健康检查要求数据库已初始化。

## 验证标准

管理端类型检查及生产构建通过；小程序类型检查和微信产物构建通过；后端测试覆盖存活/就绪、默认拒绝、错误响应及 Long 精度，Maven 打包通过。具备 Docker 时执行 Compose 验证和启动冒烟；环境缺少 Docker 时明确记录该限制。
