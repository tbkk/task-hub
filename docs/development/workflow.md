# 需求与开发流程

## 来源与适用范围

2026-09-20 参考 Puck 的 `AGENTS.md`、`.agent/workflows/feature.md`、`bugfix.md`、`db-change.md`、`frontend-change.md` 和 `release.md`，按 Task Hub 现有目录与验证命令整理。

只采用开发规范，不迁移 Puck 的业务、框架、账号、端口和部署设置。Puck 部分工作流仍使用旧 `AI_CONTEXT` 路径，本项目使用下述实际文档目录。

## 新功能

1. 阅读根目录 `AGENTS.md`、整体路线图及相关需求和现有实现，核对范围、依赖与当前进度。
2. 检查工作区改动，从 `dev1.0` 建立 `feature/<功能名>` 分支或隔离 worktree；同一功能已有分支时继续使用，不覆盖未提交工作。
3. 准备中文 PRD：目标、用户场景、范围、非目标、异常场景、可核验的验收标准。已有需求文档可作为 PRD 基线。
4. 准备中文设计：组件与模块职责、接口、数据模型、权限、状态与错误处理、测试策略；涉及界面时引用对应设计来源。
5. 准备中文计划：任务顺序、修改位置、依赖、验证命令、完成条件和外部阻塞。
6. 按计划实现，优先复用已有模式；新增需求先更新范围和计划。
7. 执行受影响模块验证，记录证据与未覆盖范围。
8. 完成 review，处理确认的问题并复验。
9. 更新进度、接口、决策及未闭环事项；按用户授权提交和合并。
10. 合并到 `dev1.0` 后做集成验证；发布合并到主分支后再次验证，不能只引用 feature 分支测试结果。

## Bug 修复

1. 记录复现步骤、预期与实际结果，结合相关代码、接口和日志定位原因。
2. 在当前分支做最小修复，不强制另建分支或补写需求、设计、计划。
3. 增加或更新能捕获问题的最小回归验证。优先为业务行为补测试；文档和低影响静态调整使用针对性核对。
4. 对权限、数据库、并发和安全问题执行专项验证。
5. 完成 review；重复出现的问题记录原因、处理方法与防回归措施。

## 数据库变更

- 先检查当前结构、迁移历史与相关接口，再新增有序增量迁移；启用 Flyway 后使用 `server/src/main/resources/db/migration/`。
- 保留已有数据；迁移兼容已有状态，不修改已应用迁移来冒充新版本。
- 同步实体、Mapper、服务、接口及前端类型，必要时同步首次初始化说明。
- 记录是否实际执行、数据库版本、执行结果及回滚或恢复办法。未执行时明确标注，不写成“迁移通过”。

## 验证命令

从对应目录执行，按变更影响选择：

| 模块 | 基础验证 | 追加验证 |
| --- | --- | --- |
| `miniprogram/` | `npm test`、`npm run typecheck`、`npm run build:h5`、`npm run build:mp-weixin` | 页面交互、窄屏、失败路径；微信能力需开发者工具/真机 |
| `admin-web/` | `npm test`、`npm run build`（包含类型检查） | 相关页面与接口交互、权限和异常路径 |
| `server/` | `mvn test`、需要交付构建时 `mvn package` | 服务健康、接口、权限、数据库与跨端联调 |
| 文档/配置 | `git diff --check`、路径与命令核对 | 配置变化对应的启动或构建验证 |

测试应验证业务约束和错误路径，不只重复实现。集成验证覆盖本次变更影响到的模块及跨端主流程；缺少真实服务、凭证或设备时记录阻塞与替代验证，不将替代结果当作真实验收。

## 文档维护

| 内容 | 位置 |
| --- | --- |
| 项目开发规则 | `AGENTS.md` |
| 需求与界面资料 | `docs/design/`；新独立 PRD 可放 `docs/prd/` |
| 功能设计 | `docs/superpowers/specs/`；跨模块架构放 `docs/architecture/` |
| 任务计划 | `docs/superpowers/plans/` |
| 阶段状态、验收和外部依赖 | `docs/superpowers/plans/2026-09-20-development-roadmap.md` |
| API 契约 | `docs/api/` |
| Review 记录（需要留档时） | `docs/reviews/` |
| 文档导航 | `docs/README.md` |

未存在的目录在首次需要时创建。以已有文档作为唯一进度来源，不再复制一套容易失去同步的项目状态文件。

## 提交与交付检查

- 检查 `git status --short` 和 diff，排除意外文件、凭证、日志和构建产物。
- 确认验证与最终代码一致，review 问题已处理，迁移执行状态明确。
- 确认相关文档已更新；提交说明围绕实际问题与最终变化。
- 提交、推送与合并遵循已有用户授权，推送前核对远程仓库和目标分支。
- 交付报告说明实现范围、验证结果、剩余工作与限制，避免将占位页面或 Mock 描述为完整业务能力。
