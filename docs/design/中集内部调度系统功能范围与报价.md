## 一、报价前提与系统范围

- 单工厂，初期1～10台车辆，使用预设且车辆可达的停靠点。
- 交付一个工人微信小程序、一个PC仓库及调度管理后台，以及配套后端服务。
- 一期采用人工选车和派单，同一预约时段按申请顺序排队；仓库可人工合并同一仓库、同一停靠点、同一预约时段的订单，一车配送。
- 工人端支持微信登录及手机号验证码登录；仓库及管理员沿用PC后台，仓库手机工作台仍为可选增项。
- 申请处理、派车、取货、异常工单及操作记录在线可查至少31天；不包含逐秒原始车辆遥测及连续历史轨迹的长期保存。
- 提供跳转九识小程序首页的普通入口，客户提供有效AppID及测试账号；目标端功能和权限由九识提供。
- 对接一家车辆厂商，即九识现有开放API和MQTT推送。
- 微信主体、服务器账户、九识接口权限、车辆及现场联调条件由客户提供和协调。
- 初期用户量、订单峰值、备份策略和可用性指标须在需求确认阶段确定；超出约定规模的架构扩容另行评估。

小程序向自有后台提交业务请求，由后台校验身份和订单权限，再调用九识API控制车辆。后台接收MQTT消息，关联车辆和任务，向小程序及管理后台提供状态。

## 二、标准版功能清单

以下仅列入现有九识API/MQTT文档明确支持，可由自有后台独立实现，或微信已有普通跳转能力支持的功能。车辆接口功能仍需使用实际账号和车辆完成联调验收。

难度按当前标准版范围评估：低为常规业务开发；中为涉及流程、权限或外部接口联动；高为涉及车辆动作、异常一致性及实车验证。高难度功能保留的是可实现的有限范围，不包含对厂商未定义行为的承诺。

| 模块 | 功能点 | 范围说明 | 实现难度 | 前提或限制 |
|---|---|---|---|---|
| 登录与身份 | 微信登录、手机号验证码登录、员工身份绑定、账号启停用 | 统一微信与手机号账号关联，采用员工白名单准入 | 中 | 客户提供微信及短信服务能力，验证码限频；短信费用另计 |
| 配送申请 | 货物名称、大小描述、接收人、电话、目的地、预约时段、备注 | 文字编辑，半小时预约；不设物料库、物料编码和库存管理 | 低 | 明确营业时段与预约容量；预约不等于保证时段内送达 |
| 常用地址 | 选择工厂停靠点、保存常用点位 | 不支持任意地址直接作为车辆目的地 | 低 | 客户及九识提供可达且与车辆绑定的停靠点 |
| 我的订单 | 列表、审批结果、详情、车辆进度、取消申请 | 合单后各发起人分别查看自己的订单和关联车辆进度 | 中 | 单个订单取消不直接取消整车任务；派发后由仓库处理取消申请 |
| 配送进度信息 | 展示当前目的地、距下一停靠点距离、路段参考耗时和数据时间 | 直接展示MQTT提供的数据；路段参考耗时指历史预估的整段耗时 | 低 | 使用currentStopId/currentStopName、currentToTargetMileage和currPlanElapsedTime；数据缺失或过期时显示暂无有效数据，不换算为实时到达时刻 |
| 扫码取货 | 扫码识别、订单与用户校验、指定格口开门、用户确认取货 | 二维码由自有系统管理；确认取货仅更新自有业务订单 | 高；实车联调 | 使用API第12节开格口，明确传入gridNos；用MQTT的doorStatus展示门状态，取货完成由用户点击确认 |
| 扫码车辆离开 | 扫码后校验订单、当前任务、停靠点、取货及门状态，用户确认后调用go | 当前站相关订单全部已取、箱门关闭、无未处理异常且任务有下一停靠点时允许操作 | 高；实车联调 | 第11节go前往下一停靠点；数据过期时禁止操作，末站不提供离开按钮 |
| 站内消息 | 受理、发车、到达、取消和异常消息列表、未读标记 | 在小程序或后台打开时查询和刷新消息 | 低 | 根据自有业务操作及已收到的有效车辆状态生成消息 |
| 仓库工作台 | 申请纵向列表、受理或驳回、按时段排队、装货确认、进入发车界面 | 发车界面显示车辆空闲/使用中，可选车、开门及派单 | 中 | 按所属仓库限制数据范围，派发前重新核对车辆状态 |
| 人工合单配送 | 仓库勾选已受理订单组建批次，分配车辆、格口并统一发车 | 同仓库、同停靠点、同预约时段合单；发车前可移出订单，发车后锁定批次 | 高 | 一个批次对应一个dispatchId，各订单独立取货；装载量由仓库判断，不做自动配载或多站路线优化 |
| 任务调度 | 人工选择车辆、点位及业务格口，创建普通任务、停靠点继续出发、停车状态下取消任务 | 自有后台管理订单与格口分配，派发后保存九识dispatchId | 高；实车联调 | API第7节创建普通任务并出发，第11节去往任务下一停靠点，第10节取消；取消要求车辆无速度，取消后停在原地，实际以接口结果为准 |
| 车辆监控 | 在线状态、配送状态、电量、位置、箱门状态、当前任务 | 展示状态更新时间，识别消息过期和离线 | 中 | 区分数据过期、MQTT链路异常及厂商明确的离线状态；实际车型字段完整性需验证 |
| 基础资料 | 车辆及停靠点同步、查询、业务配置、绑定关系展示 | 九识点位新增、删除及地图作业不包含在一期 | 低 | 查询接口已有文档；需确认账号数据权限、分页与基础资料更新规则 |
| 角色权限 | 工人、仓库人员、调度员、管理员；数据和操作权限隔离 | 工人查看本人申请或指定接收的订单；仓库及调度查看所属仓库记录；管理员查看本工厂全部记录 | 中 | 后台校验列表、详情、导出及控制操作；合单不向其他工人披露联系人信息 |
| 异常处理 | 接口失败、超时、车辆离线、取货超时、人工处理记录 | 不将接口请求成功直接视为车辆动作完成 | 高 | 需区分明确失败与执行结果未知；后者核对状态或转人工，不能承诺所有异常自动恢复 |
| 未收货异常工单 | 工人按订单提交文字反馈，仓库受理、记录结果并关闭，工人可查看进度 | 待处理、处理中、已关闭；全部处理记录留档 | 中 | 管理员查看全部；工单关闭与取货确认、车辆任务结束分别记录 |
| 订单与任务关联 | 订单、配送批次、车辆、dispatchId、目的地及格口关联，保留历次派发记录 | 同一批次共享车辆进度，各订单独立确认取货 | 高 | 使用API和MQTT车辆级状态，不依赖orderList；派发结果未知时阻止拆批重派 |
| 状态接入 | MQTT连接、重连、按任务和时间处理重复或过期消息、当前状态缓存 | 重连后查询车辆详情，并等待新消息更新其余字段 | 高 | 车辆详情按每车每秒最多一次限流；展示已获取的最新快照与时间，缺失字段标记未知，仅保存实际收到的历史消息 |
| 控制可靠性 | 本系统防重复提交、同车派单冲突控制、超时记录、当前任务核对、人工处理入口 | 超时后标记结果待核对，阻止本系统继续盲目重复下发 | 高 | API第6节可查询当前dispatchId、任务目标和车辆状态；不能明确归属的任务交由人工核对，本地锁只约束本系统操作 |
| 操作日志与记录留存 | 申请处理、合单、派单、开门、离开、取消、取货确认、工单及接口结果记录 | 在线查询及导出，保存至少31天 | 中 | 记录操作者与时间，敏感数据脱敏；按配置清理超期记录 |
| 基础统计 | 按日期和车辆统计订单，查询及Excel导出 | 不含定制大屏与复杂绩效分析 | 低 | 以自有业务数据统计，先明确完成、取消、异常的统计口径 |
| 运行维护基础 | 服务监控、错误日志、数据库备份、配置管理 | 备份保留周期与恢复目标在部署方案中明确 | 中 | 依赖客户云资源及权限；需验证备份可恢复，不包含24小时人工值守 |
| 九识小程序入口 | 用户点击并确认后跳转九识小程序首页，提示取消或失败 | 普通AppID跳转，不含免登录、车辆直达或九识内部功能开发 | 低 | 客户提供有效AppID及可测试账号；返回后刷新本系统可获取的车辆状态 |
| 项目交付 | 部署、接口联调、验收支持、源码、说明文档、一次培训 | 以远程交付为基础，驻场另计 | 中；实车联调依赖较强 | 客户及九识提供账号、完整接口资料、可用车辆和现场配合；模拟接口不能替代车辆动作验收 |

业务流程：工人申请 → 仓库受理并排队 → 同站同时间段人工合单（可选） → 装货确认 → 人工派车 → 运输 → 到达 → 扫码开门 → 各用户分别确认取货 → 各自配送订单完成。

同站订单全部已取、相关箱门状态新鲜且关闭、没有未处理异常、任务有下一停靠点时，允许扫码确认继续出发。该规则仅约束本系统下发go，九识端车辆自动离站策略需在实车联调时核对，不能以本地校验代替车端停留策略。

共享格口以客户接受共同取货为前提：同格口开门会暴露其中全部货物。要求物理隔离时，按独立格口分配并限制批次容量。未取货或未收到货进入异常工单，由仓库处理。

九识小程序仅提供跳转入口，不承诺复制九识APP全部功能；目标端功能、账号登录和操作权限由九识负责。

业务订单状态与车辆任务状态分别维护。用户确认取货只完成自有配送订单；车辆继续显示九识实际状态，只有核对车辆空闲且无当前任务后才允许本系统再次派单。车辆上报的BACK、ARRIVEHOME可作为状态展示，不据此提供返程控制操作。

## 四、维护报价与第三方费用

验收后提供3个月免费缺陷保修，修复与已确认需求及验收标准不符的问题。原交付缺陷在保修期内的修复不消耗维护额度。新增功能、业务规则变更及第三方接口重大变更不属于缺陷保修。

## 五、实施前提与接口依据

| 实施项 | 依据或实施要求 |
|---|---|
| 账号与鉴权 | API第1节获取token；客户提供appId/appKey、接口权限和MQTT接入配置，密钥只保存在后台 |
| 车辆与点位查询 | API第3～6节提供站点、停靠点、车辆列表与车辆详情；车辆详情遵守每车每秒最多一次的限制 |
| 调度与开门 | API第7、10、11、12节分别提供普通任务、取消、继续出发和开格口；联调验证成功、失败及超时展示 |
| 车辆状态 | MQTT第2、3节提供实时状态与业务状态；按vehicleName和dispatchId关联任务，并核对目的地 |
| 配送进度信息 | 展示currentStopName、currentToTargetMileage、currPlanElapsedTime及更新时间，路段参考耗时单位为分钟 |
| 取货记录 | 本系统用户确认并保存操作者、订单和时间，与箱门状态分别记录 |
| 合单与扫码离开 | 多条自有订单关联一个dispatchId；按当前停靠点校验取货状态及格口，调用go前核对下一停靠点；实车核对车端停留策略 |
| 九识小程序跳转 | 使用微信wx.navigateToMiniProgram及有效AppID实现首页跳转，不依赖目标端接受自定义参数 |
| 留存与权限 | 业务记录保存至少31天；工人按订单关系、仓库按所属仓库、管理员按本工厂校验访问权限 |
| 点位和路线 | 客户提供可用点位、车辆绑定及可达路线；地图采集不属于软件交付 |
| 联调材料 | 提供完整原始接口文档，核对缺失地址、断行字段及请求示例 |
| 实际业务规则 | 明确员工准入、时段容量、排队、批次取消申请、取货超时、共享格口及异常工单处理规则 |

取消车辆任务与取消业务订单分别处理。行驶中的订单可提交取消申请，由调度员跟进；车辆任务仅在符合接口条件时执行取消，失败或结果未知时保留处理记录。
